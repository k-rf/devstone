# PR コメント口調・書式ガイド

PR コメントを作成する際は、フラットで実証的かつ建設的なトーンに揃える。
（参考実例: PR #62 `https://github.com/k-rf/devstone/pull/62`）

## 1. 基本口調と禁止事項

- **文体**: 敬語（です・ます調）を使わない、フラットで客観的なタメ口寄りの常体で統一する。
- **事実ベース**: 推測や印象論を避け、ファイル名・行番号・識別子・実測数値を起点に語る。
- **意図の尊重**: 設計上の選択やトレードオフの余地がある箇所は決めつけず、
  意図確認や方針別の分岐を添えて提案する。
- **禁止事項**:
  - ぞんざい・攻撃的・見下した表現（「なんでこうしたの」「ひどい」「あり得ない」等）
  - チャット側のロールプレイ演出
    （一人称「私」、キャラ口調・偉人引用、過剰な感嘆符や絵文字の連打）
  - 敬語の混在（「〜してください」「〜いかがでしょうか」「〜と考えます」）
  - `[Blocker]` / `[Nit]` などの機械的ラベルの連発（強度差は文末表現で自然に伝える）

## 2. 強度別の文末表現

| 強度・役割                | 使う場面                                                   | 文末表現の例                                                                                                           |
| :------------------------ | :--------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------- |
| 観察・事実指摘            | 実装と記述の差や重複など、まず事実を示す                   | `〜してるね` / `〜になってるね` / `〜ズレがあるね` / `〜が被ってるね`                                                  |
| 修正必須（`must`）        | 明確な誤り、仕様未達、規約違反、境界の破綻、回帰検知の欠落 | `〜直してほしい` / `〜直す必要があるかな` / `〜見直す必要があると思う`                                                 |
| 強い推奨（`should`）      | 変更耐性、DRY、保守性、可読性、テスト品質の明確な改善      | `〜見直した方がいいと思う` / `〜にしたいかな` / `〜方が変更耐性が高いと思う` / `〜方がすっきりする` / `〜方が親切かな` |
| 軽微な提案・確認（`nit`） | 設計意図の確認、方針分岐の相談、軽微な改善提案             | `〜必要ある？` / `〜かな` / `〜んじゃない？` / `〜確認しておきたい` / `〜検討した方がよさそう`                         |

## 3. サマリーコメントの構成とテンプレート

サマリーコメントは冒頭の概要一文と、`主な確認ポイント：` 以下の太字カテゴリ別箇条書きで構成する。
絵文字は冒頭ステータス（指摘ありなら `⛔`、指摘 0 件だが未実施観点・未確認項目ありなら `⚠️`、
全対象確認済みで問題なしなら `✅`）の 1 個までに留める。

### 指摘がある場合のテンプレート

`not run` の観点や未確認項目がある場合は、末尾の箇条書きまたは一文で未検証範囲を併記する。

```markdown
⛔ PR #<number> を見て、<確認した主な観点>あたりで気になったところにコメント残した。

主な確認ポイント：

- **<観点グループ 1>**: `<識別子やファイル>` の<事実・実測値の要約>
- **<観点グループ 2>**: `<識別子やファイル>` の<事実・設計上の論点>
- **<観点グループ 3>**: `<テストやドキュメントの論点>`
```

### 指摘が 0 件だが未実施観点・未確認項目がある場合のテンプレート

```markdown
⚠️ PR #<number> を見て、<確認できた観点>では特に気になる点はなかったけど、
<未実施観点や未確認項目>は未確認のままになってる。
```

### 全対象観点を確認済みで指摘が 0 件の場合のテンプレート

```markdown
✅ PR #<number> を見て、<確認した主な観点>を一通り確認したけど、特に気になる点はなかった。
```

## 4. インラインコメントの構成と記述ルール

1. **記述順序**: 原則として次の 3 段構成で簡潔にまとめる。
   `事実・根拠（行番号・識別子・実測数値）→ 影響・問題点 → 改善案／確認事項`
2. **方針の分岐**: 複数の解釈や設計方針が成り立つ場合は、箇条書きで選択肢を並べる。
   - 例:
     - 「方針 A なら、JSDoc を実態に合う記述へ直してほしい。」
     - 「方針 B の意図なら、値の方を見直す必要があるかな。」
3. **横展開の統合**: 同じ原因・同パターンの問題が他ファイルにもある場合は、
   代表 1 箇所のコメント本文内で `(xxx.ts も同じ)` のようにまとめて言及し、
   同一内容のコメントを複数箇所へ連投しない。
4. **良い例と避けるべき例**:
   - **良い例（事実・実測・改善案）**:
     `retry-policy.ts` でも同じだけど、JSDoc だとタイムアウト既定値 `3000ms` って書いてあるのに、
     実装の `DEFAULT_TIMEOUT_MS` は `30000` になってるね。
     `parseDuration` の実測でも 30 秒待ちになるから、意図した値に合わせて JSDoc か定数のどちらかを直してほしい。
   - **良い例（設計意図の確認）**:
     `InternalClientConfig` と `RawResponseMapper` って `src/index.ts` から外部公開する必要ある？
     公開面を絞った方が将来の内部構造変更時の破壊的変更を防げるから、内部型に留めた方が変更耐性が高いと思う。
   - **避けるべき例**:
     - `私としてはここは分割すべきだと思います。すぐに直してください！`（一人称・ロールプレイ調・敬語混在・過剰な感嘆符）
     - `[Major] DRY 違反です。共通化してください。`（機械的ラベル・敬語・根拠不足）
     - `なんで同じコードコピペしたの？ひどい設計だね。`（攻撃的・ぞんざい）
